# 票 20：天文数字拦截 + 首独立小数行强信号锚定 + 置信度阈值校准

- Owner: QoderCN
- Created: 2026-09-21
- Resolved: 2026-09-21

## 现象

用户导入微信账单详情（淘宝平台商户，-15.40）报「提取失败」，耗时 ~39s；
0.4.5（含前两项修复）仍复现同样错误。

## 诊断（实时 logcat）

```
E2E_OCR_LINE[4] [0.73] 89          ← 状态栏碎片，刚过 0.7 线
E2E_OCR_LINE[9] [1.00] 15.40       ← 负号被 OCR 丢失，无符号裸数字
SMOKE_LITERT_OK ms=35296 len=269
  "amountPaid": 89000000…（200 多位零）
```

模型抄状态栏「89」生成天文数字 → 撑爆 256 token 上限 → JSON 截断解析失败；
生成 256 token 也是 35s 的来源。0.4.5 的金额上限拦截只在「JSON 合法」时可达，
截断发生在解析之前，故无效。

## 修复（三层）

- `MIN_LINE_SCORE` 0.7 → **0.78**：掐掉 0.73 的「89」这类祸根。
  0.85 曾尝试——30 图闸门 100%→96.7%（order_12 哨兵图拍摄照片正常行被误伤），
  0.78 兼顾两侧（真机截图垃圾行 0.64–0.79、拍摄照片正常行 <0.85）
- `DraftNormalizer`：金额 ≥100 万抛「金额超出合理范围」（JSON 合法时兜底）
- `OcrPostProcessor.AMOUNT_STANDALONE`：区块首个「整数.两位小数」独立行
  （15.40 / -29.90 / -370.00，负号丢失也命中）升为强信号参与锚定

## 附加

- 队列卡片计时：提取中实时秒数（500ms 步进），完成/失败显示耗时（用户要求）
- ImportItem 新增 startedAtMs / durationMs

## 验证

- `:engine:test` + `:app:testDebugUnitTest` 全绿
- 30 图闸门：0.78 版 100% PASS（score078 报告）；10 样本金额 100%
- versionCode 14 / 0.4.6 装机

## 遗留观察

- 阈值二分过程：0.85 → order_12 回归 → 0.78 通过。order_12 是有效哨兵
- 生成 256 token 的耗时上限：噪音行裁剪（P1）减 prefill，decode 等上游 INT4
