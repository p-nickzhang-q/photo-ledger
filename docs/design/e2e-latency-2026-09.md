# 端到端提取耗时现状与优化路线（票 05 实测）

日期：2026-09-14。状态：现状记录 + 优化路线待票 10（模型管理）落地。

## TL;DR

票 05 真机端到端跑通，质量达标（Draft 与桌面 harness 4/4 字段一致），但**单张截图全链路 ~10 分钟**，其中 LLM 推理段占 99.7%。这在「后台批量提取」场景勉强可用，在「拍照即出结果」场景不可用。本文记录实测数据、瓶颈分析与优化路线，供票 07（队列）做交互设计、票 10（模型管理）做优化决策。

## 实测数据（2026-09-14，order_01，真机）

| 段 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| OCR（PP-OCRv4 mobile 三件套，ONNX Runtime，4 线程） | 1465ms | 0.3% | 13 行，含 det/rec |
| 后处理（订单块识别、文本拼装） | ~0ms | - | 在共享引擎内，微秒级 |
| LLM（Qwen3-0.6B Q8_0，n_ctx 2048，6 线程，GBNF 约束） | **594598ms** | **99.7%** | ~1.4 tok/s |
| **总计** | **596067ms** | | |

环境：vivo V2183A（天玑 9000 级，arm64，11.7GB RAM），模型 mmap 加载 604MB，峰值 RSS 1.32GB。

## 瓶颈分析

**1. 解码速度是根因。** ~1.4 tok/s 意味着每生成 100 token 需 ~70s。GBNF 约束下的 Draft JSON 输出在数百 token 量级（订单块文本 + 全字段 JSON 骨架），直接线性放大到 ~10 分钟。速度与模型量化档位、线程数、SoC 持续多核吞吐强相关，与输入内容基本无关——无法靠「简化单张输入」显著改善。

**2. CPU 线程数已接近收益上限。** 当前 6 线程。该档位 SoC 的性能核通常 1 个 X 系列 + 3 个 A7xx，6 线程已会让部分线程落到能效核；继续加线程边际收益递减且加剧发热降频。

**3. prompt 结构放大了解码量。** 当前 prompt 把候选订单块的 OCR 文本行完整拼入（含商品名、营销文案等无关行），模型需要先「阅读」再输出完整 JSON；若输出契约要求商家名等字段逐字复述，解码 token 数随之膨胀。

## 优化路线（按投入/收益排序）

| # | 手段 | 预期效果 | 风险/代价 | 归属 |
|---|---|---|---|---|
| 1 | **Q4_K_M 量化**（0.6B） | 2-2.5× 提速（~2.8-3.5 tok/s），单张降到 ~4-5 分钟；内存峰值同步减半 | 质量需重跑闸门（30 张硬字段）；Q4 对 0.6B 这种小模型精度损伤风险高于大模型 | 票 10 |
| 2 | **输出瘦身**：Draft JSON 只输出必要字段、缩短枚举值、压缩空白 | 解码 token 数 -30-50%，耗时同比降 | 需改 grammar 与解析层（共享引擎内改，两端同时生效） | 票 10 或 07 |
| 3 | **输入瘦身**：后处理先过滤无关 OCR 行（营销、导航类），只拼订单块相关行 | prefill 量降（对解码段无直接帮助，但缩短上下文后每步解码也更快） | 过滤规则可能误删字段行，需闸门回归 | 票 07/10 |
| 4 | **flash attention / mmap 调优、KV 量化** | ~10-30% 提速 | 收益有限，属锦上添花 | 票 10 |
| 5 | GPU offload（OpenCL/Vulkan） | 理论 3-5×，但该 SoC GPU 对 llama.cpp 支持成熟度未知 | 集成与维护成本高，驱动兼容性碎片化 | 不推荐 v1 |

**基准建议**：票 10 落地 #1+#2 后以「单张 ≤ 2 分钟」为阶段目标；若 Q4_K_M 闸门不达标则退回 Q8_0 + 仅做 #2，接受 ~5 分钟/张并靠票 07 队列的异步交互消化。
