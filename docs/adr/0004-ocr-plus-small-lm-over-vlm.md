# 提取路线改用轻量 OCR + 文本小模型，替代端到端 VLM

日期：2026-09-11。状态：已接受（取代 ADR-0001 的「VLM 端到端」路线与 ADR-0002 的 4B VLM 选型）。

## 背景

ADR-0001 选定 VLM 端到端路线（截图 → Qwen3-VL-4B → Draft），前提假设是 4B VLM 在目标机（vivo V2183A，8GB+ RAM）上的提取耗时可接受。桌面质量闸门管线（票 01）在同一 CPU 环境的实测推翻了这一假设：

- 1080×2400 真机订单截图，Qwen3-VL-4B Q4_K_M 在桌面 10 核 CPU（GTX 1650 因 WSL 驱动缺 libcuda 不可用）上 vision prefill 单张约 3-5 分钟。vision token 数随像素面积增长，是耗时大头；解码段在 GBNF 约束下仅 ~100 token，占比很小。
- 手机 SoC 的持续多核吞吐约为该桌面 CPU 的 1/5-1/10，推算单张 15-40 分钟，远超「随手记一笔」的交互预期；降分辨率与 GPU offload 可改善但均有不确定性，而 4B 模型的 2.8GB 体积本身已是存储与加载负担。

## 决定

提取管线改为两段式：

1. **轻量 OCR**（PP-OCRv5 系，桌面经 RapidOCR/ONNX Runtime 已验证，单张秒级；移动端对应 Paddle Lite / ONNX Runtime 部署，模型 ~20MB）：截图 → 文本行（含坐标）。
2. **文本小模型 + GBNF 约束解码**（llama.cpp 运行时不变；主选 Qwen3-0.6B/1.7B Q8_0，桌面双档对比后定稿）：OCR 文本行 → Draft JSON。此阶段复用票 01 已建成的全部引擎核心：prompt 构造、GBNF 生成器、JSON 解析与口径归一（engine 模块）、llama-server transport。

## 理由

- 端侧速度从「分钟级/张」降到「秒级/张」：OCR 毫秒级 + 0.6B-1.7B 文本模型数百 token 以内的 prefill 与生成，手机 CPU 可承受。
- 引擎核心、运行时、构建链、验收方法学（质量闸门）全部保留，路线切换的沉没成本只有 mmproj 与 4B 权重本身。
- 「文本 → JSON」是纯文本任务，0.5B-2B 级模型 + grammar 约束即可胜任（调研报告 §4 已给出同构先例）；OCR 丢失的版面信息由文本行坐标保留兜底。
- ADR-0001 为 OCR 路线预留的备胎描述（PP-OCRv5 + 小模型）与本决定一致，只是主备互换。

## 后果与风险

- ADR-0001 中「VLM 端到端」升格为备选路线：若 OCR 路线在质量闸门不达标（OCR 丢版面/丢字段导致结构化失败），退回 VLM 并接受降分辨率 + GPU offload 的优化路径。
- ADR-0002 的运行时选择（llama.cpp）继续有效；其中 Qwen3-VL-4B 的模型选型部分失效，由 Qwen3-0.6B/1.7B 取代；MiniCPM-V 4.5 对比项随 VLM 主路线一并搁置。
- 新增风险：OCR 对订单截图的行序与字段粘连（如「下单时间2026-09-10 11:19」）需要结构化 prompt 明确容错；实付款口径在 OCR 文本中依赖「实付款」「实付」等关键词邻近性，质量闸门需把「口径取错」列为专项统计项。
- 票 01 的验收结论（llama.cpp 多模态 + GBNF 组合可行性、集成方式）不受本决定影响，照常入票供后续票引用。
